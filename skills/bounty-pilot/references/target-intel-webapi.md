# Target Intelligence + Web/API Lab (experimental)

This is the optional Web/API extension to the evidence-first Bounty Pilot Lab.
It adds **three evidence-oriented workflows**: fresh program/scope changes,
JavaScript changes, and controlled authorization checks.

It does NOT discover new bounty programs on its own, poll targets, or perform
a blanket scan. All inputs are saved snapshots supplied by the operator. The
only network-capable helper is web_auth_lab.py, which defaults to dry-run,
permits only owned test accounts + approved GET paths, and requires explicit
Mac-side authorization before any request. Results are research leads, NOT
verified reports.

## 1. Program & Scope Radar

Import the actual retained history exported by
gkdataio/security-research-library (CC BY 4.0 applies to its original data):

    python3 scripts/program_scope_radar.py \
      --history /private/program-change-history.json \
      --out /private/history-leads.json

This parses recorded scope additions/removals and keeps the recording
timestamp. It does NOT confuse the timestamp with the effective date.

To compare explicit snapshots from a scope inventory, use:

    python3 scripts/program_scope_radar.py \
      --before /private/scope-20261106.json \
      --after /private/scope-20261107.json \
      --out /private/scope-leads.json

Normalized format (one snapshot; the next one uses a later snapshot_at):

~~~json
{
  "schema_version": 1,
  "snapshot_at": "2026-11-07T15:00:00Z",
  "programs": [
    {
      "id": "example",
      "platform": "Bugcrowd",
      "program_url": "https://bugcrowd.com/engagements/example",
      "program_type": "paid_bounty",
      "verified_at": "2026-11-07T14:58:00Z",
      "in_scope": [
        {"name": "api.example.test", "asset_type": "api", "bounty_eligible": true}
      ],
      "out_of_scope": []
    }
  ]
}
~~~

The parser also accepts the top-level programs.json format of the security
research library. Because that format has no capture timestamp, the adapter
uses its latest per-program verified_at date as a fallback comparison time;
that timestamp is **not** when a scope policy became effective.

bbscope v2 can collect multi-platform public scopes. Export and normalize its
rows into the schema above *outside this helper*. This branch does not claim
native bbscope JSON parity for formats it has not validated. Do not supply
platform authentication secrets or cookies to these scripts.

Lead types include new/missing programs, added/removed in/out-of-scope assets,
changed published program type and changed bounty eligibility. A missing
listing is not proof of program closure. Recheck exact official policy,
account ownership, automation policy, and actual bounty eligibility.

## 2. JavaScript Change Intelligence

Save selected in-scope JS assets manually, e.g., from authorized browser
sessions. Use one stable logical asset ID across deploys even if a content hash
changes the emitted file name.

Create two manifests, each next to its copied JS files:

~~~json
{
  "schema_version": 1,
  "captured_at": "2026-11-07T15:00:00Z",
  "assets": [
    {
      "id": "main-app-bundle",
      "script_url": "https://app.example.test/_next/static/chunks/app.js",
      "file": "app.js"
    }
  ]
}
~~~

    python3 scripts/js_change_intel.py \
      --before /private/older/manifest.json \
      --after /private/newer/manifest.json \
      --out /private/js-leads.json

By default it uses a simple bounded URL regex and hash comparisons. The
optional **jsluice** integration is a local AST-backed URL extractor: install
a vetted, pinned version of jsluice separately on the Mac and opt in:

    python3 scripts/js_change_intel.py \
      --before /private/older/manifest.json \
      --after /private/newer/manifest.json \
      --out /private/js-leads-ast.json --use-jsluice

The process can only read local JS source files and receives no cookies or
request headers. It must still run in a disposable, isolated environment:
untrusted JS parser bugs are possible. No target network requests happen.

Output: new/removed endpoint candidates, unique query-parameter **names**
(values omitted), original file SHA256, and coarse keyword tags such as
authorization, payments and session/origin. JavaScript source, query values
and apparent secrets are never placed in the resulting JSON. A changed hash
is NOT an authorization bypass, and static extraction misses computed routes.
A new URL should be checked against live official bounty scope before testing.

## 3. Web/API Authorization Lab

Review a local OpenAPI 3 JSON file generated by mitmproxy2swagger from a
user-owned/authorized HAR or mitmproxy capture. Optional YAML support requires
PyYAML and uses safe_load. The parser never resolves remote references:

    python3 scripts/api_surface_import.py \
      --spec /private/openapi.json \
      --out /private/get-review-queue.json

The result lists GET paths and likely object-id parameters but is NOT an
executable test plan. Select concrete IDs from **two accounts you own**,
with unique synthetic markers visible only to each owner. Confirm that the
information is intended to be private.

Create this private two-account test plan:

~~~json
{
  "schema_version": 1,
  "base_url": "https://api.example.test",
  "program_url": "https://example.test/security",
  "scope_confirmed_at": "2026-11-07T17:00:00Z",
  "authorization_confirmed": true,
  "automation_permitted": true,
  "test_actors": {
    "owner": {"bearer_env": "BP_TEST_OWNER_AUTH"},
    "outsider": {"bearer_env": "BP_TEST_OUTSIDER_AUTH"}
  },
  "cases": [
    {
      "id": "owner-invoice",
      "private_resource_confirmed": true,
      "owner_resource": "/api/invoices/101",
      "outsider_control_resource": "/api/invoices/202",
      "owner_marker": "PRIVATE-OWNER-TEST-INVOICE-101",
      "outsider_control_marker": "PRIVATE-OUTSIDER-TEST-INVOICE-202"
    }
  ]
}
~~~

First validate **without network requests**:

    python3 scripts/web_auth_lab.py \
      --plan /private/my-test-plan.json --out /private/auth-dry.json

Only after verifying the official policy permits the test, the test accounts
are fully controlled and the host belongs to the exact scope, execute from a
disposable Mac environment with environment-only bearer tokens:

    python3 scripts/web_auth_lab.py \
      --plan /private/my-test-plan.json --out /private/auth-result.json \
      --allowed-host api.example.test --confirm-authorized --execute

The executable mode additionally requires the manifest's authorization and
automation assertions to be true, a recent timestamp (30 days), macOS, a
matching HTTPS hostname, and different credential variables per account.

Every case performs just three HTTP GET requests, in order:
- owner reads its own object (positive baseline; owner marker present);
- outsider reads owner's object (possible unauthorized access);
- outsider reads its own object (positive independent control).

No redirect is followed; no mutation, brute forcing, URL guessing, cookies,
response bodies, bearer tokens or raw markers are written to output. Up to
12 cases, bounded read size and 0.5-second pacing. An HTTP status or a matching
marker by itself is not proof. The output remains a candidate until independent
review establishes private ownership, effective authorization, reproducibility
and bounty scope. A GET endpoint can still have side effects; never execute
without authorizing it.

Do not commit the plan, HAR, source snapshots with secrets, tokens, receipts or
outputs to public GitHub. Use a private folder *outside* the target checkout.

## Testing

Mac-only self-hosted workflow at
.github/workflows/target-intel-webapi-mac.yml runs the new Python test suite
and existing evidence-first smoke tests. The synthetic tests never perform
network requests; one code path uses mocked HTTP calls, not real targets.

    python3 -m unittest discover -s tests \
      -p 'test_target_intel_webapi.py' -v

A green unit suite verifies parsers/gates only, NOT bug-finding quality.
Real effectiveness must be measured separately with blinded Web/API
cases and source revisions, including negative controls and duplicate outcomes.
